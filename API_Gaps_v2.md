# ЧАСТИНА 1 — API GAPS (технічні)

## 1. ВІДСУТНІЙ ТИП НОДИ: `loadFile`

**Проблема:** Немає способу через API вказати боту завантажити файл з бази даних на старті сесії. Всі боти курсу починають з читання файлів попередніх ботів (`cashflow_articles`, `business_process` тощо), але в MCP це неможливо задати — Claude в system prompt має `context.cashflowArticles` як змінну, але немає механізму що наповнює її перед стартом діалогу.

**Що потрібно:**
```json
{
  "type": "loadFile",
  "data": {
    "fileType": "cashflow_articles",
    "outputVar": "context.cashflowArticles",
    "onMissing": "ask" | "skip" | "block"
  }
}
```

**`onMissing` варіанти:**
- `"ask"` — бот сам запитує студента надати файл
- `"skip"` — продовжує без файлу
- `"block"` — зупиняє сесію і показує повідомлення про prerequisite

**Боти які потребують цього:** всі, починаючи з 2.2 (13 з 14).

## 2. ВІДСУТНІЙ МЕХАНІЗМ: prerequisite check перед стартом

**Проблема:** Логіка розблокування блоків не може бути задана через MCP. Бот стартує незалежно від наявності потрібних файлів.

**Що потрібно:** Поле в конфігурації бота:
```json
{
  "prerequisites": {
    "files": ["cashflow_articles", "pl_articles"],
    "onFail": {
      "message": "Спочатку пройди урок 2.1 — там збираємо статті Cashflow і P&L.",
      "suggest_bot": "bot-2-1-articles"
    }
  }
}
```

**Боти:** 2.2, 2.3, 3.2, 3.3, 4.1, 4.2, 4.3, 4.4, 4.5, 5.1, 5.2, 5.3.

## 3. ВІДСУТНІЙ ТИП НОДИ: `httpRequest`

**Проблема:** Боти 2.2, 2.3, 3.2, 4.4, 5.2 мають викликати Apps Script через HTTP POST. Зараз це описано в system prompt Claude — що неправильно архітектурно.

```json
    "onError": "fallback" | "throw"
  }
}
```

## 4. ВІДСУТНІЙ МЕХАНІЗМ: передача контексту між сесіями

**Проблема:** Кожна сесія ізольована. Боти курсу мають читати `context.*` з попередніх сесій того ж користувача.

**Що потрібно:** При старті сесії — автоматично підтягувати збережені `fileType` в `context.*`.

Маппінг:
```
cashflow_articles    → context.cashflowArticles
pl_articles          → context.plArticles
business_process     → context.businessProcess
business_process_v2  → context.businessProcessV2
cashflow_table_url   → context.sheetsUrl
combined_table_url   → context.combinedUrl
financial_mechanics  → context.financialMechanics
salary_processes     → context.salaryProcesses
payment_processes    → context.paymentProcesses
balance_articles     → context.balanceArticles
balance_table_url    → context.balanceUrl
```

## 8. СЕРЕДОВИЩА: Telegram і Instagram в API і UI

**Контекст:** Агент вже додає підтримку двох середовищ (Telegram і Instagram). Потрібно щоб це відображалось і в API, і в UI.

**Що потрібно в API:**

При `get_funnel` і `update_funnel` — додати поле `channel`:
```json
{
  "bot": {
    "id": "...",
    "name": "Bot 2.1 Articles",
    "slug": "bot-2-1-articles",
    "channel": "telegram" | "instagram",
    "channelLink": "https://t.me/your_bot?start=lesson_2_1",
    "channelUsername": "@your_bot_username"
  }
}
```

`channelLink` — платформа будує автоматично:
- Telegram: `https://t.me/{botUsername}?start={trigger}` де trigger береться з Start-ноди
- Instagram: посилання на Instagram Direct або відповідний entry point

**Що потрібно в `list_funnels`:** повертати `channel` і `channelLink` для кожної воронки.

**Що потрібно в UI:**

На картці воронки в списку — іконка середовища (літак для TG, камера для IG) + клікабельне посилання "Відкрити в Telegram →" яке відкриває бота з правильним deep link.

На сторінці редактора в хедері — поруч з назвою: середовище + пряме посилання (копіювати одним кліком).

## 9. ЛОГИ НА НОДАХ + РЕЖИМ МОНІТОРИНГУ

**Проблема:** Зараз немає способу побачити де "болить" конкретна нода або де застряг конкретний підписник.

**Два підходи — доповнюють один одного:**

**Підхід А — індикатори на нодах (завжди видно в редакторі):**

Кожна нода отримує кольоровий індикатор в правому верхньому куті:
- 🟢 — все ок, помилок немає
- 🟡 — є попередження (довгий час відповіді, часті retry)
- 🔴 — є помилки за останні 24 години

Клік на індикатор → панель справа з логами саме цієї ноди: останні N викликів, помилки, середній час.

**Підхід Б — окремий режим "Live" (перемикач в хедері редактора):**

Два режими канвасу:
- **Edit** (поточний) — редагування flow
- **Live** — моніторинг в реальному часі

В режимі Live:
- На нодах показуються аватарки або точки підписників які зараз на цій ноді
- Клік на точку → переписка цього підписника в реальному часі
- Ноди з помилками підсвічуються червоним
- Стрілки між нодами показують "потік" — скільки підписників пройшло за останні 24 год

**Рекомендація:** Підхід А — в першу чергу (дешевше, одразу корисно). Підхід Б — після того як є базова аналітика по нодах.

**Що потрібно в API для підходу А:**
```
get_node_stats(botId, nodeId, period?)
→ { errorCount, avgDurationMs, passCount, lastError }
```

## 10. ВІДСУТНІЙ МЕТОД API: читання логів через MCP

**Проблема:** Через MCP можна читати і редагувати flow, але не можна отримати логи сесій або помилки. Для повноцінного налагодження та моніторингу ботів потрібен доступ до логів через той же інтерфейс.

**Що потрібно — методи:**
```
get_session_logs(botId, userId?, limit?)  → список сесій з повідомленнями
get_api_logs(botId?, service?, limit?)    → API виклики (claude, telegram, google_sheets)
get_errors(botId?, resolved?, limit?)     → помилки з stack trace
```

**Навіщо:** Щоб Claude через MCP міг не тільки змінити flow, але й подивитись що пішло не так в конкретній сесії і відразу виправити.

## A. СТРУКТУРА ГОЛОВНОГО МЕНЮ

**Поточне (некоректне):** Воронки / Дашборд / Сесії / Юзери / API логи / Помилки — все в одному рівні без логічної групи.

**Має бути:**

```
├── Воронки          (головна робоча секція)
├── Дашборд          (огляд метрик)
├── Підписники       (загальний список по всіх воронках)
├── Конектори        (список зовнішніх інтеграцій)  ← обговорення нижче
├── Логи             (помилки + API логи — в одному місці)
├── Налаштування     (тільки для адмінів)
│   ├── MCP посилання для Claude
│   ├── Webhook URL платформи
│   ├── Глобальні ключі (APPS_SCRIPT_URL тощо)
│   └── Управління користувачами
└── Вийти
```

**Зміни:**
- "Юзери" → "Підписники" (якщо про студентів/лідів) або окремо "Підписники" і "Користувачі" (адміни/оператори системи)
- "API логи" + "Помилки" → об'єднати в "Логи" з вкладками
- "Налаштування" — новий розділ тільки для адмінів
- Прибрати "Сесії" з першого рівня — сесії мають бути всередині воронки або підписника

## B. РОЛІ КОРИСТУВАЧІВ

**Поточне:** одна роль (@admin_owner), немає розмежування.

**Що потрібно:**

| Роль | Можливості |
|------|-----------|
| **Super Admin** | Все. Бачить всіх користувачів, всі воронки, може змінювати ролі |
| **Admin** | Свої воронки + воронки які додали в доступ. Бачить підписників своїх воронок |
| **Viewer** | Тільки перегляд статистики і сесій по призначених воронках |

**Управління користувачами (тільки Super Admin):**
- Додати / заблокувати / змінити роль
- Назначити воронки конкретному адміну
- Переглянути активність: коли заходив, що робив

## C. РОЗДІЛ "ВОРОНКИ"

**Поточне:** просто список воронок з мінімальною інфо.

**Для адмінів — дві вкладки:**
- **"Мої воронки"** — де він власник
- **"Воронки інших"** — де він viewer або куди йому дали доступ

**Картка воронки в списку має показувати:**
- Назва + slug
- Проект
- К-сть підписників (активних за 7 днів / всього)
- К-сть сесій за тиждень
- Статус (активна / пауза / архів)
- Дата останньої зміни flow

**Дії на картці:**
- **Відкрити flow** (редактор)
- **Підписники** → список підписників цієї воронки
- **Логи** → API логи + помилки тільки по цій воронці
- **Редагувати** → змінити назву, опис, slug, статус
- **Дублювати** → створити копію воронки
- **Архівувати / Видалити**

## G. КОНЕКТОРИ — чи потрібен окремий розділ?

**Твоє питання:** чи варто мати "Конектори" в меню, якщо вони додаються через API.

**Моя думка:** так, варто, але як read-only список в UI. Логіка:

- Конектори (Google Sheets, Telegram, Apps Script, зовнішні API) додаються і налаштовуються через MCP API
- В UI — тільки список підключених конекторів зі статусом (активний / помилка / не налаштований)
- Кнопка "Перевірити з'єднання" для кожного
- Посилання на документацію як додати через API

**Чому не повний CRUD в UI:** якщо конектори додаються через API (і ти хочеш це зберегти), то UI-форма дублює логіку і її треба підтримувати паралельно. Краще — API first, UI як дзеркало.

## H. ЛІВА ПАНЕЛЬ РЕДАКТОРА — групування нод

**Поточне (зі скріншоту):** всі типи нод в одному плоскому списку — Start / Повідомлення / Claude AI / JavaScript / Умова / Конектор / Зберегти файл / Очікування.

**Що змінити — згрупувати в секції з розгортанням:**

```
▼ БАЗОВІ
   🚀 Start
   💬 Повідомлення
   ⏳ Очікування

▼ ЛОГІКА
   ⚡ JavaScript
   ✕  Умова (if/else)

▼ AI
   🧠 Claude AI

▼ ДАНІ
   💾 Зберегти файл
   📂 Завантажити файл       ← новий тип (Gap #1)
   🌐 HTTP запит             ← новий тип (Gap #3)

▼ КОНЕКТОРИ
   📱 Telegram
   📸 Instagram
   📊 Google Sheets
   ⚙️  Apps Script
   + Додати конектор         ← відкриває список доступних
```

**Чому це важливо:**
- Конектори — окрема секція в панелі нод, не окремий розділ меню. Саме тут вибираєш і перетягуєш на канвас
- Нові типи нод (`loadFile`, `httpRequest`) одразу з'являться у відповідній секції після реалізації
- Список конекторів розширюється — нові підключення одразу доступні в редакторі

**Поведінка секції "Конектори":**
- Показує тільки ті конектори які налаштовані в Налаштуваннях (є ключі/токени)
- Якщо конектор не налаштований — показується з іконкою замка і підказкою "Налаштувати →"
- Перетягнув конектор на канвас → з'являється нода з полями специфічними для цього конектора

## I. РЕДАКТОР ВОРОНКИ — що ще додати

**Поточне (з скріншоту Bot 2.1):** є канвас з нодами, панель типів нод зліва, ключі воронки справа. Виглядає добре.

**Що додати:**

1. **Назва + опис воронки** — редагувати прямо з хедера (зараз тільки назва відображається, клікнути не можна)

2. **Статус воронки** — перемикач "Активна / Пауза" прямо в хедері редактора

3. **Кнопка "Тест"** — запустити воронку в тестовому режимі без реального Telegram, прямо в браузері (симулятор чату)

4. **Версії** — "Зберегти версію" + можливість відкотитись до попередньої (зараз є тільки "Зберегти")

5. **Кнопка "Підписники"** в хедері редактора → швидкий перехід до підписників саме цієї воронки

6. **Кнопка "Логи"** в хедері → логи саме цієї воронки

7. **Дублювати ноду** — правий клік на ноді → скопіювати

8. **Коментарі до нод** — поле для нотаток розробника (не впливає на flow)

## I. ДАШБОРД — що покращити

**Поточне:** 4 картки (Всього сесій: 0, Активних сесій: —, Юзерів: 1, API викликів сьогодні: —). Порожньо, нічого не показує.

**Що додати:**

1. **Графік активності** — сесії/повідомлення за останні 7/30 днів
2. **Топ воронок** — по к-сті активних підписників
3. **Топ помилок** — що найчастіше падає
4. **Вартість API** — токени Claude × ціна → сума за день/місяць (важливо для контролю витрат)
5. **Нові підписники** — графік приросту
6. **Точки відвалу** — де підписники найчастіше зупиняються (топ-5 нод де сесія завершилась без результату)

## ПІДСУМОК: пріоритети

### Технічні gaps (API)

| Пріоритет | Gap | Вплив |
|-----------|-----|-------|
| 🔴 Критично | `loadFile` нода | Без цього боти 2.2–5.3 не мають вхідних даних |
| 🔴 Критично | Передача context між сесіями | Кожен бот починає "з нуля" |
| 🔴 Критично | `create_edge` метод | Нові ноди не підключені до flow |
| 🟡 Важливо | `httpRequest` нода | Apps Script виклики некоректно в system prompt |
| 🟡 Важливо | prerequisite check | Студент може запустити бот без потрібних файлів |
| 🟡 Важливо | `APPS_SCRIPT_URL` keys | Потрібно додати після деплою Apps Script |
| 🟡 Важливо | Логи через MCP (`get_session_logs` тощо) | Claude не може діагностувати проблеми без логів |
| 🟡 Важливо | `channel` + `channelLink` в API воронки | Без цього не знаєш середовище і немає прямого посилання |
| 🟡 Важливо | `get_node_stats` для індикаторів на нодах | Основа для моніторингу де "болить" |
| 🟢 Бажано | `multiTurnEnd` сигнал | Flow не контролює момент завершення діалогу |
