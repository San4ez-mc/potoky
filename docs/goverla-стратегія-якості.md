# goverla: стратегія якості — «правки → нуль»

> **Головний документ стратегії.** Перед будь-якою правкою бота goverla (і будь-якого магазину на shopAgent) — читати його.
> Затверджено власником 13.10.2026. Оновлюється при кожному переході етапу: розділ «Статус» і «Журнал».

## 1. Навіщо

Кількість правок в Edits не зменшувалась, хоча 200 з 259 закрито. Мета — не закрити ці правки, а зробити так, щоб
вони переставали виникати: **0 розмов без відповіді, < 1% розмов бота з помилкою, нові правки — лише нові класи.**

- У 178 з 198 виправлених категорій після «виправлено» знову з'являлись правки тієї самої категорії.
- За 4 тижні ~330 змін коду агента, ~250 з них — «виправлення». `policy.js` виріс з 863 до 2 845 рядків, у ньому 120 датованих латок, 45 вгадувань змісту регуляркою, 70 перевірок «що бот спитав» за текстом, 181 розгалуження.
- 187 з 259 правок без категорії, 179 подав Олексій, скріншоти без посилання на розмову.
- ≥ 21 правка — наслідок наших же змін.

**Чому правки не зменшуються:**
1. Лікуємо випадки, а не класи: кожен фікс закриває один шлях.
2. Архітектура сама виробляє помилки: код угадує зміст повідомлень.
3. Немає мірила якості: правки залежать від того, скільки встиг побачити Олексій.
4. Зміни йдуть у бойовий режим без страховки: денні деплої, тести після фіксу, суддя-ШІ з підігнаними критеріями.
5. Великі зміни робляться без переліку наслідків: Zernio→Meta, вимкнення тестового режиму.
6. Межа «бот / менеджер» розмита.
7. Процес правок дорогий: скріншот без розмови.
8. Дані магазину частково в коді.

## 3. Принципи роботи (обов'язкові для Claude)

1. **Клас, а не випадок.** Кожна правка належить класу. Спершу перевіряємо, чи детектор класу її бачить. Якщо ні — спершу детектор і тест класу, потім фікс.
2. **«Виправлено» означає «підтверджено».** Правка закривається, лише коли на прогоні реальних ходів у цьому класі нуль (з етапу 1). До того — «виправлено (без прогону)».
3. **Заморожування латок.** Поки йде перебудова, дрібні випадки не латаємо в `policy.js`. Одразу виправляється лише критичне: гроші, мовчання бота, скарга клієнта. І завжди з тестом класу.
4. **Деплой лише через `platform/scripts/deploy.sh`**, у вікні 21:00–08:00 за Києвом. Удень лише `--critical "причина"`.
5. **Великі зміни** (канал, режими, ключі, вимкнення тестового режиму) — лише з письмовим переліком «що це зачіпає» і тіньовим днем.
6. **Критерії тестів не підганяються** під результат. Якщо критерій хибний — окремий коміт з поясненням чому.
7. **Звіт власнику — у частці розмов з помилкою**, а не в кількості правок.
8. **У кінці кожної відповіді** — що власник і Олексій мають зробити на поточному етапі.

## 4. Етапи і ворота

Наступний етап починається лише тоді, коли попередній показав результат у цифрах.

| Етап | Що робимо | Ворота |
|---|---|---|
| **0. Бачити** (1–2 дні) | Детектори класів, щоденний звіт, сторож «клієнт чекає менеджера», знімок пам'яті перед ходом, деплой-скрипт із вікном і плавною зупинкою, кнопка ⚠ → Edits | Щоденний звіт приходить і збігається з реальністю |
| **1. Не ламати** (3–4 дні) | Прогін нового коду на 300–500 вчорашніх ходах перед деплоєм (блок при новому спрацюванні детектора); FunnelTest з перевірками кодом; «виправлено» лише після тесту класу | Прогін ловить усі відомі класи на історичних прикладах |
| **2. Топ-3 класи** (тиждень) | Канал (звірка невідповіданих), межа «бот / менеджер» (CRM-замовлення з нікнеймом, пауза з терміном, бот бачить замовлення в CRM), товар і контекст (прибрати вгадування, Ф2) | < 2% розмов з помилкою 3 дні поспіль |
| **3. Прибрати фабрику помилок** (2–3 тижні) | Переробка «потік з агентом» (план `glittery-conjuring-sparkle`) через тіньовий режим на прогоні; тексти, умови і сітки в CRM; перемикання ключем | Тінь не гірша за старий двигун на прогоні й живих розмовах |
| **4. Стале життя** | Кожна правка — відомий клас (чому детектор не зловив?) або новий клас (детектор і тест, потім фікс); щотижнева пачка рішень власника; щотижневий звіт динаміки | < 1% розмов з помилкою, далі до 0,5% |

**Цілі:** 0 розмов без відповіді понад 5 хв · < 2% після етапу 2 · < 1% після етапу 3 · 0 повторів категорії після «виправлено».

### Класи детекторів (етап 0)

| Код | Що ловить |
|---|---|
| `no_reply_bot` | клієнт написав, бот не на паузі, відповіді немає 10+ хв |
| `no_reply_manager` | клієнт написав у розмову, яку веде менеджер, відповіді немає 10+ хв (окремо, не в частці бота) |
| `repeat_ask` | те саме прохання 3+ рази в розмові |
| `asked_known_hw` | просить зріст і вагу, які клієнт уже написав |
| `duplicate_bot` | той самий текст двічі поспіль за 3 хв |
| `send_failed` | відповідь не дійшла (збій каналу) |
| `loop_handoff` | бот здався: «щоб не ганяти по колу» |
| `complaint` | скарга / роздратування клієнта |
| `open_question` | хід закінчився з відкритим питанням (зі знімка) |
| `sale_on_status` | питав про своє замовлення, а бот продавав (зі знімка) |
| `product_unknown` | приніс пост / рекламу / фото, а товар не визначено (зі знімка) |
| `ai_down` | ШІ не відповів, хід пропущено (зі знімка) |

Новий клас помилки → новий детектор тут **до** фіксу.
