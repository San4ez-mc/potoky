# FINEKO Flows — загальний стандарт воронок

> Це **загальний стандарт** для всіх воронок платформи. Специфіка фінансового курсу — в skill `funnel-writing-fineko`.
> Читай разом із `platform/CLAUDE.md` (інфраструктура, уроки з помилок).
>
> **ПОРЯДОК РОБОТИ:** перед тим як додати/змінити будь-яку ноду — прочитай §2 (каталог нод)
> і обери тип за призначенням, а не «схоже підійде». Перед здачею — пройди §4 (антипатерни) і §6 (чекліст).

## 0. Залізні правила (порушувати не можна)

### 1 — весь функціонал у нодах, редаговано з канваса
Усе, що робить воронка, — **в нодах flow-визначення**, редагується з канваса. Заборонено «частина в ноді, частина захардкоджена у скрипті». Виняток — реалізація типу ноди в `testSession.js` (двигун, не конфіг).
**Наслідок:** великий JS-код ноди тримай у файлі репо (напр. `easydrop-cart-code.js`) і підвантажуй у патч — але **джерелом істини лишається нода в БД**, а патч-файл її відтворює.

### 2 — ключі тільки у ключах воронки, перевага збереженим конекторам
- Жодних ключів у `.env` (env — лише `PORT`, `DATABASE_URL`, `MCP_SECRET`).
- Перевага — **збережені конектори** (instance UUID з `list_connectors`): `connectorId: "<uuid>"`.
- Сирий ключ у `funnelKey` — виняток, якщо використовується в ОДНІЙ воронці.
- `TELEGRAM_CONNECTOR_ID` — виняток (у кожного бота свій токен).

### 3 — нема ноди для функції → додай тип ноди у ТРЬОХ місцях
1. **Двигун:** `apps/api/src/services/testSession.js` (`if (node.type === '...')`).
2. **MCP:** `NODE_TYPES` у `apps/mcp/src/tools-flows.js`.
3. **Фронт:** `apps/admin/src/components/funnel/NodeTypes.jsx` — і мапа компонентів (щоб не білий квадрат), і `NODE_PALETTE` (icon/label/color/description/defaultData).

### 4 — заповнити ОБИДВА описи воронки
`description` (людям: що робить, для кого) + `goal` (для AI: ціль одним рядком). Порожній опис = воронка не готова.
**Опис має відповідати реальності** — якщо в описі «ПОТРЕБУЄ переробки», а це вже зроблено, опис треба оновити.

### 5 — кожна нода в try/catch + логування зовнішніх викликів
Падіння ноди не валить сесію. Усі зовнішні виклики (Claude, HTTP, Telegram, платежі) — в `api_calls`.
**Додатково:** статус доставки повідомлень пиши в `flowRuntime.deliveryLog` (видно у вкладці «Ноди» → «Доставка») — інакше «чому не прийшло» неможливо діагностувати.

### 6 — після створення обовʼязково тест-прогін
Тест-сесія / `/start <slug>` / POST на вебхук. Перевір: повідомлення йдуть, кнопки показуються, claude-нода відпрацьовує, сповіщення доходять, `pm2 logs platform-api` чистий, вкладка API показує виклики.
**Мінімум 10 тест-покупців з різною поведінкою** для продажних воронок (див. §5).

### 7 — жодних демо/тестових даних у проді
Демо-товари, фейкові ціни, плейсхолдери «Постачальник по накидках», тестові адреси — **не залишати**. Особливо небезпечні **фолбеки на демо-дані**: краще чесно сказати «не визначив» і покликати людину, ніж підставити вигадане.

### 8 — зовнішні мутації за замовчуванням у DRY-RUN
Будь-яка нода, що створює замовлення/платіж/запис у чужій системі, має ключ `*_DRY_RUN` (дефолт `1`) і гард `if (context.testMode) return ...`. Перехід у бій — тільки з явного дозволу власника.

## 1. Як обрати ноду (швидкий маршрутизатор)

| Треба… | Нода |
|---|---|
| показати фіксований текст / картинку-посилання / кнопки | `message` |
| поговорити з клієнтом, зрозуміти намір, витягти дані | `claude` (`mode:'dialog'`) |
| один раз згенерувати текст із даних (без діалогу) | `claude` (`mode:'single'`) |
| AI, що САМ викликає інструменти в циклі | `agent` |
| порахувати/перетворити/зібрати дані, звернутись до API | `js` |
| розгалужити потік | `condition` |
| пауза або очікування події/кнопки | `wait` |
| надіслати фото товару | `sendPhoto` |
| надіслати файл/PDF | `sendDocument` / `sendFile` |
| прийняти файл від клієнта | `readFile` |
| зберегти/дістати проміжний артефакт сесії | `saveFile` / `loadFile` |
| згенерувати DOCX за шаблоном | `generateDocument` |
| **сповістити менеджера в групу** | **`notifyTg`** (не `notifyAdmin`) |
| викликати сторонній HTTP API | `httpRequest` (просте) або `js` (складна логіка) |
| платіж / виписка / браузер-агент | `connector` |
| чекати оплату WayForPay | `wait_payment` |
| відповісти з бази знань | `knowledgeBase` або `claude` з `useKb:true` |

## 2. Каталог нод (звіряй ПЕРЕД вибором)

> Поля наведені так, як їх реально читає двигун (`testSession.js`). Якщо поля нема в списку — воно ігнорується.

### Керування потоком

**`start`** — вхідна точка. `{ label, trigger:'/start <slug>' }`
Один старт на воронку. Кілька воронок на боті — різні `trigger`.

**`condition`** — розгалуження. Два формати:
- простий: `{ condition: "context.x === true" }` → ребра з handle `true` / `false`;
- мульти: `{ conditions:[{id,label,expression}] }` → **порядок ребер = порядок умов**, збіг першої виграє, інакше перше ребро.
⚠️ **Обидві гілки мають вести кудись осмислено.** False-гілка «в нікуди» або в ноду, яка без цих даних не працює, — типова причина зависань.
⚠️ Роби **fail-forward**: у «поганий» бік іди лише на ЯВНУ ознаку (напр. `!/^(ні|нет|no)/i.test(...)`), а не «якщо не точно так».

**`wait`** — пауза/очікування. `{ mode:'delay'|'event', unit:'minutes'|'hours', duration, eventKey, buttonText, waitMessage }`
`mode:'event'` — чекає подію (натискання кнопки). Не став `wait` там, де просто треба дочекатись відповіді клієнта — це робить `claude`-нода сама.

**`js`** — довільний код. `{ code, label }`
Доступно: `context, user, session, input, keys, fetch, Buffer, FormData, Blob, console, crypto`; можна `await`.
Повертає обʼєкт → **мержиться в `context`** (root-рівень!). `return {}` — нічого не змінює.
Використовуй для: розрахунків, звернень до API з логікою, нормалізації даних, службових прапорців.

### Спілкування

**`message`** — статичний текст. `{ text, label, variants:[], buttons:[[{text,url|callback_data}]], attachmentUrl, attachmentFileName }`
- Інтерполяція: `{{context.x}}`, `{{env.KEY}}`, `{{user.firstName}}`.
- `variants` — випадковий вибір з масиву; **порожній `variants:[]` = використати `text`** (лишиш старі варіанти — вони «воскреснуть»).
- ⚠️ **Instagram не показує inline-кнопки** — там посилання давай **текстом** у `text`.

**`claude`** — AI-нода. `{ mode:'dialog'|'single', systemPrompt, exitCondition, outputVar, messagesTemplate, model, maxTokens, temperature, connectorId, useKb, speakFirst }`
- `exitCondition`:
  - `json_output` (дефолт) — виходить, щойно у відповіді зʼявився JSON; видимий текст очищається від JSON;
  - `user_confirms` — виходить на згоду користувача;
  - `keyword:<слово>` — на слово у відповіді моделі;
  - `markdown_output` — на markdown;
  - `none` — не виходить сам (для `mode:'single'` генерації).
- `useKb:true` — підмішує топ-3 з вектор-бази (`VECTOR_URL`+`VECTOR_TOKEN`) і дозволяє `{"handoff":true}`.
- `outputVar` — куди покласти розпарсений JSON (`context.X`).
- ⚠️ `messagesTemplate` — **тільки прості рядки** (обʼєкти ламають JSON → модель отримує «Продовжуємо діалог»).
- ⚠️ Бюджет системного промпту ≤3000 токенів.

**`agent`** — AI з інструментами в циклі. `{ systemPrompt, tools, maxIterations, outputVar, dialogMode, startTrigger, messagesTemplate, model, maxTokens, finishTool }`
Бери, коли модель має САМА вирішувати, який інструмент викликати. Для лінійного сценарію — не треба, дорожче й непередбачуваніше.

**`knowledgeBase`** — пошук по вбудованих блоках. `{ blocks:[{id,title,content}], contextKey }`
Для невеликого статичного FAQ. Для великої/змінюваної бази — вектор-база + `claude useKb:true`.

### Медіа та файли

**`sendPhoto`** `{ photoVar, caption }` — фото з `context.<photoVar>`. Порожній `caption` = без тексту (не пиши плейсхолдер «📸 Фото»).
**`sendDocument`** `{ fileKey, fileType, fileVar, url, fileName, caption }` — файл/PDF.
**`sendFile`** `{ fileUrl, fileName, caption }` — файл за прямим URL.
**`readFile`** `{ outputVar, maxChars }` — приймає документ від клієнта, кладе текст; мета в `context.readFileMeta`.
**`saveFile`** `{ fileType, contentVar, template }` / **`loadFile`** `{ fileType, outputVar, onMissing }` — чекпоінти довгих сценаріїв.
**`generateDocument`** `{ template, sourceVar, filename, sendToUser }` — DOCX за шаблоном.

### Сповіщення

**`notifyTg`** ⭐ — **основний спосіб** сповістити менеджера. `{ targetKey:'ADMIN_TELEGRAM_ID', message }`
Бере `chat_id` **прямо з ключа воронки** і токен з `TELEGRAM_BOT_TOKEN` воронки. Передбачуваний, працює з групами.

**`notifyAdmin`** — легасі. `{ targetKey|telegramId, message, notifyUser, userMessage }`
Має фолбеки на системні ключі → у мультимагазинному сетапі може піти не туди («bot can't initiate conversation with a user»). **Бери `notifyTg`, якщо немає причини інакше.**

### Інтеграції

**`httpRequest`** `{ url, method, headers, body|bodyFields, outputVar, responseField, label }` — простий виклик API.
Складніше (кілька кроків, cookie-сесія, парсинг HTML) — роби в `js`.

**`httpEncode`** `{ sourceVar, outputVar }` — base64.

**`connector`** `{ connectorType, action, outputVar, ... }` — типи: `wayforpay`, `ibanoplata`, `monobank`, `browser_agent`.
- `ibanoplata`: `create_invoice` (amount, paymentPurpose, expirationHours) → `context.ibanPayUrl`/`ibanInvoiceUid`; `delete_invoice` (invoiceUid).
- `monobank`: `get_statement` (windowHours) → `context.monoStatement`; `mark_consumed` (txId) — антидубль.
- `browser_agent`: `replay`/`agent`/`read`.
- ⚠️ Ці типи читають ключі з **funnelEnv**, `savedConnector` необовʼязковий.

**`wait_payment`** `{ timeoutHours }` — блокує до вебхука WayForPay.
**`fbEvent`** `{ eventName, value, currency, testEventCode }` — CAPI, best-effort.
**`fetchTelegramProfile`** `{}` — тихо кладе `context.tg_bio`, `context.tg_photo_url`.

## 3. Архітектурні правила потоку

1. **Одна нода = одна дія.** Не змішуй «презентація + запит даних» в одному тексті, якщо далі є окрема нода для цього запиту — буде дубль.
2. **Кожна нода має ОДИН вихідний ланцюжок** (або явне гілкування через `condition`). Паралельного fan-out немає — виконається лише перше ребро.
3. **`context` — тільки root-рівень.** Не клади дані у вкладені `flowRuntime.*`.
4. **Кожне видиме повідомлення закінчується питанням або чітким наступним кроком.** Похвала без питання («чудовий вибір!») зупиняє діалог.
5. **Тихі ноди** (які лише витягують JSON) не мають писати видимий текст — інакше клієнт бачить два повідомлення підряд.
6. **Немає глухих кутів:** після будь-якої гілки клієнт або отримує питання, або справу передано людині.
7. **Handoff:** якщо кличемо людину — ставимо `adminEngaged`, пишемо клієнту одне повідомлення і **замовкаємо**. Передбач спосіб повернути бота (кнопка ▶ у сесії або автоматичне відновлення за подією).
8. **Критичні рішення — детерміновані.** Прохання «хочу людину», підтвердження оплати, ліміти — regex/код, а не «модель зрозуміє». LLM — доповнення, не єдиний запобіжник.

## 4. Антипатерни (реальні помилки — не повторювати)

**A1. Демо-фолбек у проді.** Ключ `DEFAULT_AD_ID` підставляв демо-товар усім незіставленим — реальні клієнти отримували «Бомбер Мілітарі» замість накидок.
➡️ Не робити фолбеків на демо-дані. Не визначили — спитати або покликати людину.

**A2. Гілка `false` у ноду, якій бракує даних.** `n_have_product[false] → n_size` — бот питав розмір товару, якого не знає, і вигадував ціни.
➡️ Малюючи `condition`, одразу опиши обидві гілки словами. Якщо для гілки нема осмисленого продовження — це не condition, а handoff.

**A3. Осиротілі ноди після рефакторингу.** Лишались `n_pay_cond`, `n_verify`, `n_avail_reply` — сміття на канвасі.
➡️ Після перебудови перевіряй: ноди з 0 вхідних і 0 вихідних (крім `start`), недосяжні, тупики. Видаляй.

**A4. Модель вигадує значення для `json_output`.** Промпт просив `yes|no`, модель віддавала `{"ready":"waiting"}` → умова `false` → клієнт застрягав після «Так».
➡️ У промпті: перелічити ДОПУСТИМІ значення, **явно заборонити інші**, і сказати «поки нема явної відповіді — json НЕ додавай». Умову робити fail-forward.

**A5. Дубль повідомлень.** `n_welcome` питав зріст/вагу і наступна нода теж.
➡️ Перед додаванням тексту перевір, що наступна нода не питає те саме.

**A6. Сповіщення пішло «в нікуди».** `notifyAdmin` брав системний особистий `ADMIN_TELEGRAM_ID` → `Forbidden: bot can't initiate conversation with a user`.
➡️ Використовуй `notifyTg` + ключ воронки. Після додавання сповіщення — **перевір, що воно реально дійшло** (лог доставки).

**A7. Підміна обʼєкта в контексті без очистки залежних полів.** При виборі позиції з набору товар успадкував кольори набору → бот питав неіснуючий колір.
➡️ Підміняючи `context.product` (чи будь-який складений обʼєкт), перезаповни ВСІ залежні поля (колір, розміри, фото, offers) або обнули їх.

**A8. Матчинг «по будь-якому полю».** Резолвер складу набору шукав артикул у всіх кастом-полях → набір знаходив сам себе через поле «Допродажі».
➡️ Матч тільки по конкретних полях; **виключай сам обʼєкт** зі списку кандидатів.

**A9. Успіх інтеграції визначався «на око».** Перевіряв текст відповіді, а реальний успіх був **302-редиректом** → нода двічі рапортувала «не створилось», хоча замовлення створилось.
➡️ Зʼясуй справжній контракт (статус/редирект/поле), логуй сирі відповіді. Не вгадуй.

**A10. Патч перезаписав ручні міграції.** Промпт `n_color` правився міграцією, а `patch --apply` повертав старий.
➡️ **Patch-файл — єдине джерело істини** для постійних змін. Міграції — одноразові; те, що має жити, переноситься в патч.

**A11. Дрейф сервера.** На сервері бували незакомічені зміни — пуш міг їх затерти.
➡️ Перед `pull`: `git fetch` + `git status` на сервері.

**A12. Медіа й текст приходять окремими вебхуками.** Клієнт шерить рілс і одразу пише «Скільки?» — текст може прийти першим, товару ще нема → хибний висновок «товар не визначено».
➡️ Не роби незворотних висновків з одного повідомлення; передбач відновлення, коли потрібні дані прийдуть наступними.

**A13. Тестові дані в чужій системі.** Ставив CT_1005 у CRM клієнта для тесту.
➡️ Тимчасові зміни в зовнішніх системах — тільки з поверненням у вихідний стан у `finally`, і сказати про це власнику.

**A14. Обмеження каналу.** Instagram: **немає inline-кнопок**, але **є альбом до 10 фото** в одному повідомленні. Telegram — навпаки.
➡️ Перевір можливості каналу до того, як будувати UX (і не стверджуй «неможливо», не перевіривши документацію).

**A15. Плейсхолдер замість підпису.** `sendPhoto` слав текст «📸 Фото» окремим повідомленням.
➡️ Порожній підпис = нічого не слати.

## 5. Тестування воронки

**Обовʼязково прогнати ≥10 покупців з різною поведінкою:**
класика (повна оплата) · часткова оплата · згода на допродаж · відмова від допродажу · односкладні відповіді/ігнор · питання поза базою знань · прохання менеджера · неправильне/неоднозначне місто · «передумав» · торг/знижка · невідомий товар · параметри поза сіткою розмірів.

Для кожного перевір: фінальна нода осмислена, немає зациклень, `adminEngaged` там де треба, замовлення створене, сповіщення дійшло (лог доставки), у трейсі немає помилок нод.

- Сесія → вкладка **«Ноди»**: вхід/вихід кожної ноди, **гілка** condition (`branch → target`), API-виклики, помилки, лог доставки.
