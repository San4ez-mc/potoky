# ЧАСТИНА 1 — API GAPS (технічні)

## 1. ВІДСУТНІЙ ТИП НОДИ: `loadFile`

**Проблема:** Немає способу через API вказати боту завантажити файл з бази даних на старті сесії. Всі боти курсу починають з читання файлів попередніх ботів, але в MCP це неможливо задати.

**Що потрібно:**
```json
{
  "type": "loadFile",
  "data": {
    "fileType": "cashflow_articles",
    "outputVar": "context.cashflowArticles",
    "onMissing": "ask" | "skip" | "block"
  }
}
```

`onMissing`:
- `"ask"` — бот запитує студента надати файл
- `"skip"` — продовжує без файлу
- `"block"` — зупиняє і показує повідомлення про prerequisite

**Боти які потребують:** всі починаючи з 2.2 (13 з 14).

---

## 2. ВІДСУТНІЙ МЕХАНІЗМ: prerequisite check перед стартом

**Проблема:** Бот стартує незалежно від наявності потрібних файлів. Студент може запустити бот 3.2 не маючи cashflow_articles.

**Що потрібно:**
```json
{
  "prerequisites": {
    "files": ["cashflow_articles", "pl_articles"],
    "onFail": {
      "message": "Спочатку пройди урок 2.1 — там збираємо статті Cashflow і P&L.",
      "suggest_bot": "bot-2-1-articles"
    }
  }
}
```

**Боти:** 2.2, 2.3, 3.2, 3.3, 4.1, 4.2, 4.3, 4.4, 4.5, 5.1, 5.2, 5.3.

---

## 3. ВІДСУТНІЙ ТИП НОДИ: `httpRequest`

**Проблема:** Боти 2.2, 2.3, 3.2, 4.4, 5.2 мають викликати Apps Script через HTTP POST. Зараз це описано в system prompt Claude — що архітектурно некоректно.

**Що потрібно:**
```json
{
  "type": "httpRequest",
  "data": {
    "url": "{{context.appsScriptUrl}}",
    "method": "POST",
    "bodyTemplate": {
      "type": "cashflow",
      "articles": "{{context.cashflowArticles}}"
    },
    "outputVar": "context.sheetsUrl",
    "responsePath": "spreadsheetUrl",
    "onError": "fallback" | "throw"
  }
}
```

## 4. ВІДСУТНІЙ МЕХАНІЗМ: передача контексту між сесіями

**Проблема:** Кожна сесія ізольована. Боти курсу мають читати context.* з попередніх сесій того ж користувача.

**Що потрібно:** При старті сесії — автоматично підтягувати збережені fileType в context.*.

Маппінг:
```
cashflow_articles    → context.cashflowArticles
pl_articles          → context.plArticles
business_process     → context.businessProcess
business_process_v2  → context.businessProcessV2
cashflow_table_url   → context.sheetsUrl
combined_table_url   → context.combinedUrl
financial_mechanics  → context.financialMechanics
salary_processes     → context.salaryProcesses
payment_processes    → context.paymentProcesses
balance_articles     → context.balanceArticles
balance_table_url    → context.balanceUrl
```

## 6. ВІДСУТНІЙ ТИП НОДИ: `multiTurnEnd`

**Проблема:** Flow не контролює момент завершення діалогу Claude — платформа не бачить коли треба переходити до saveFile.

**Що потрібно:**
```json
{
  "type": "claude",
  "data": {
    "completionSignal": "<OUTPUT_TAG>",
    "outputVar": "context.articles_result",
    "onComplete": "save_result"
  }
}
```

## 7. ВІДСУТНІЙ МЕТОД API: `create_edge`

**Проблема:** Нові ноди додані через `add_node` не з'єднані ні з чим. Редагування edges через MCP недоступне.

**Що потрібно:**
```json
// create_edge
{ "botId": "...", "source": "node_A", "target": "node_B" }

// або update_edges — повна заміна
{ "botId": "...", "edges": [{ "source": "A", "target": "B" }] }
```

**Зараз:** saveFile для pl_articles у боті 2.1 (node_1778531261129) не підключена.

## 8. СЕРЕДОВИЩА: Telegram і Instagram в API і UI

**Контекст:** Агент вже додає підтримку двох середовищ. Потрібно щоб це відображалось в API.

**Що потрібно в `get_funnel` і `list_funnels`:**
```json
{
  "bot": {
    "id": "...",
    "name": "Bot 2.1 Articles",
    "channel": "telegram" | "instagram",
    "channelLink": "https://t.me/your_bot?start=lesson_2_1",
    "channelUsername": "@your_bot_username"
  }
}
```

`channelLink` будується автоматично з тригера Start-ноди:
- Telegram: `https://t.me/{botUsername}?start={trigger}`
- Instagram: посилання на Direct entry point

## 9. ВІДСУТНІЙ МЕТОД API: читання логів через MCP

**Проблема:** Через MCP можна читати і редагувати flow, але не логи. Claude не може діагностувати проблеми без доступу до сесій.

**Що потрібно:**
```
get_session_logs(botId, userId?, limit?)  → сесії з повідомленнями
get_api_logs(botId?, service?, limit?)    → API виклики
get_errors(botId?, resolved?, limit?)     → помилки зі stack trace
get_node_stats(botId, nodeId, period?)    → статистика по ноді
```

# ЧАСТИНА 2 — UI/UX ПРАВКИ

## A. СТРУКТУРА ГОЛОВНОГО МЕНЮ

**Поточне:** Воронки / Дашборд / Сесії / Юзери / API логи / Помилки — все в одному рівні.

**Має бути:**
```
├── Воронки
├── Дашборд
├── Підписники
├── Конектори        ← read-only список, API-first
├── Логи             ← API логи + помилки об'єднано
├── Налаштування     ← тільки адмінам
└── Вийти
```

Прибрати "Сесії" з першого рівня — сесії мають бути всередині воронки або підписника.

---

## B. РОЛІ КОРИСТУВАЧІВ

| Роль | Можливості |
|------|-----------|
| **Super Admin** | Все. Всі воронки, всі юзери, зміна ролей |
| **Admin** | Свої воронки + призначені. Підписники своїх воронок |
| **Viewer** | Тільки перегляд статистики і сесій |

Управління (тільки Super Admin): додати / заблокувати / змінити роль / назначити воронки.

---

## C. РОЗДІЛ "ВОРОНКИ"

**Для адмінів — дві вкладки:** "Мої воронки" / "Воронки інших"

**Картка воронки показує:**
- Назва + slug + іконка середовища (TG / IG)
- Пряме посилання (channelLink) — копіювати одним кліком
- К-сть підписників (активних / всього)
- Сесій за тиждень
- Статус (активна / пауза / архів)
- Дата останньої зміни

**Дії на картці:**
- Відкрити flow (редактор)
- Підписники
- Логи
- Редагувати (назва, опис, slug, статус)
- Дублювати
- Архівувати / Видалити

---

## D. РОЗДІЛ "ПІДПИСНИКИ"

"Юзери" → "Підписники" (студенти/ліди, не адміни системи).

**Додати колонки:** Воронок (скільки), Останній контакт, Прогрес.

**Фільтри:** проект / воронка / дата / активність.

**Сторінка підписника:**
- Список воронок зі статусом
- **Переписка** — повні діалоги (бот справа, підписник зліва)
- **Файли** — всі згенеровані файли з переглядом вмісту
- API виклики таймлайном
- Помилки пов'язані з цим підписником

---

## E. РОЗДІЛ "ЛОГИ"

Об'єднати "API логи" + "Помилки" в одному розділі з вкладками:
```
[Всі] [Claude] [Telegram] [Google Sheets] [Помилки]
```

Фільтри: воронка / підписник / дата / статус. Пошук по вмісту.

Кожен запис розгортається → request + response JSON.
Помилки → кнопка "Вирішено" + посилання на сесію.

Також: передавати логи через MCP API → Claude може отримати логи по воронці і одразу запропонувати виправлення.

## G. КОНЕКТОРИ — read-only в UI, API-first

Конектори (Google Sheets, Telegram, Instagram, Apps Script) керуються через MCP API. В UI — тільки список підключених зі статусом і кнопкою "Перевірити з'єднання".

Повний CRUD в UI не потрібен — дублює логіку і збільшує підтримку.

## H. ЛІВА ПАНЕЛЬ РЕДАКТОРА — групування нод

**Поточне (зі скріншоту):** всі типи нод в одному плоскому списку без поділу.

**Має бути — секції з розгортанням:**

```
▼ БАЗОВІ
   🚀 Start
   💬 Повідомлення
   ⏳ Очікування

▼ ЛОГІКА
   ⚡ JavaScript
   ✕  Умова (if/else)
   🔀 A/B тест          ← новий (розподіл підписників на гілки)

▼ AI
   🧠 Claude AI

▼ ДАНІ
   💾 Зберегти файл
   📂 Завантажити файл  ← новий (Gap #1)
   🌐 HTTP запит        ← новий (Gap #3)

▼ КОНЕКТОРИ
   📱 Telegram
   📸 Instagram
   📊 Google Sheets
   ⚙️  Apps Script
   + Додати конектор
```

Конектор в панелі:
- Показується тільки якщо налаштований (є ключ)
- Якщо не налаштований — іконка замка + "Налаштувати →"
- Перетягнув → нода з полями специфічними для конектора

## I. МОЖЛИВОСТІ НОД — що допрацювати

Поточні ноди примітивні порівняно з аналогами (Smartsender, ManyChat). Нижче — що має бути в кожній.

### Нода "Очікування" (Wait)

**Поточне:** порожньо, "Немає налаштувань".

**Що потрібно:**

| Налаштування | Опис |
|---|---|
| **Тривалість** | хвилини / години / дні / тижні (число + одиниця) |
| **До конкретного часу** | наприклад, до 10:00 наступного дня |
| **До конкретної дати** | дата з календаря |
| **Дні тижня** | надіслати тільки в пн-пт (не в вихідні) |
| **Часовий пояс** | по часовому поясу підписника або фіксований |
| **Час доставки** | "тихі години" — не надсилати з 22:00 до 9:00 |

Приклад UI: `Зачекати [2] [години] → надіслати тільки в [пн-пт] з [9:00] до [21:00] за [часовим поясом підписника]`

---

### Нода "Умова" (Condition)

**Поточне:** є нода, але невідомо які умови підтримує.

**Що потрібно:**

| Категорія | Умови |
|---|---|
| **Дані підписника** | поле = / ≠ / містить / не містить значення |
| **Теги** | має тег / не має тегу |
| **Активність** | відкрив повідомлення / натиснув кнопку / пройшов кроки N |
| **Файли** | має файл типу X / не має |
| **Час** | поточний час / день тижня / дата |
| **Кількість сесій** | більше N / менше N |
| **Значення context** | context.variable = значення |

Оператори: AND / OR між умовами. Гілки: "Так" / "Ні" / "Не визначено".

---

### Нода "Повідомлення" (Message)

**Що потрібно розширити:**

| Можливість | Опис |
|---|---|
| **Кнопки** | inline-кнопки (до 8) з текстом і дією (URL / наступна нода / тег) |
| **Медіа** | фото, відео, документ, аудіо як attachment |
| **Змінні** | `{{firstName}}`, `{{context.sheetsUrl}}` прямо в тексті |
| **Форматування** | bold, italic, code (Markdown для TG) |
| **Швидкі відповіді** | варіанти відповіді кнопками під полем вводу |
| **Затримка між повідомленнями** | якщо кілька повідомлень підряд — пауза між ними (імітація друку) |

---

### Нода "Claude AI"

**Що потрібно розширити:**

| Налаштування | Опис |
|---|---|
| **Модель** | вибір моделі (haiku / sonnet / opus) |
| **Температура** | слайдер 0–1 |
| **Max tokens** | ліміт відповіді |
| **Режим** | Single turn (один запит-відповідь) / Multi-turn (діалог до сигналу завершення) |
| **Completion signal** | рядок або regex що тригерить перехід до наступної ноди |
| **Fallback** | якщо Claude повернув помилку → альтернативна нода |
| **Вартість** | показувати приблизну вартість виклику (токени × ціна) |

---

### Нода "JavaScript"

**Що потрібно:**

| Можливість | Опис |
|---|---|
| **Доступ до context** | читати і писати context.* змінні |
| **Вбудований редактор** | з підсвіткою синтаксису і автодоповненням |
| **Тест прямо в редакторі** | запустити скрипт з тестовими даними і побачити результат |
| **Timeout** | максимальний час виконання (наприклад, 5 секунд) |
| **Логування** | `console.log()` пише в логи ноди |

---

### Нова нода: "Тег" (Tag)

**Чого зараз немає взагалі.** Є у Smartsender, ManyChat, будь-якому серйозному інструменті.

| Дія | Опис |
|---|---|
| **Додати тег** | присвоїти підписнику тег (наприклад, "block_2_done") |
| **Видалити тег** | зняти тег |
| **Перевірити тег** | використовується в ноді Умова |

Теги — основа сегментації: можна надсилати повідомлення тільки тим хто має/не має певний тег, фільтрувати підписників, відстежувати прогрес.

---

### Нова нода: "A/B тест"

**Чого зараз немає.** Розподіляє підписників на гілки з заданими відсотками:

```
[A/B тест]
├── Варіант А (50%) → гілка А
└── Варіант Б (50%) → гілка Б
```

Після завершення — статистика по гілках (конверсія, відвал, час проходження).

---

### Нова нода: "Перейти до" (Jump to)

Перенаправити підписника до іншої ноди або іншої воронки. Корисно для:
- Повторного використання частин flow
- Виходу з циклу
- Переходу між воронками при завершенні блоку

---

### Нова нода: "Оновити поле підписника"

Зберегти значення з context до профілю підписника (не до файлу):
```json
{ "field": "last_block_completed", "value": "{{context.blockNumber}}" }
```

Потім використовується в умовах і фільтрах.

## J. РЕДАКТОР ВОРОНКИ — загальні покращення

1. **Назва + опис** — редагувати прямо з хедера
2. **Статус** — перемикач Активна / Пауза в хедері
3. **Кнопка "Тест"** — симулятор чату в браузері без реального Telegram

6. **Дублювати ноду** — правий клік → копіювати
7. **Коментарі до нод** — нотатки розробника (не впливають на flow)
8. **Пошук по нодах** — знайти ноду по назві або тексту
9. **Мініатюра канвасу** — навігація по великому flow внизу справа

## ПІДСУМОК: пріоритети

### Технічні gaps (API)

| Пріоритет | Gap | Вплив |
|-----------|-----|-------|
| 🔴 Критично | `loadFile` нода | Без цього боти 2.2–5.3 не мають вхідних даних |
| 🔴 Критично | Передача context між сесіями | Кожен бот починає "з нуля" |
| 🔴 Критично | `create_edge` метод | Нові ноди не підключені до flow |
| 🟡 Важливо | `httpRequest` нода | Apps Script виклики некоректно в system prompt |
| 🟡 Важливо | prerequisite check | Студент може запустити бот без потрібних файлів |
| 🟡 Важливо | `APPS_SCRIPT_URL` keys | Потрібно додати після деплою Apps Script |
| 🟡 Важливо | Логи через MCP (`get_session_logs` тощо) | Claude не може діагностувати проблеми |

## F1. СХОВИЩЕ ФАЙЛІВ МІЖ БОТАМИ (User Storage)

**Проблема:** Файли зберігаються через `saveFile`, але немає єдиного сховища на рівні користувача яке всі боти бачать і з якого читають. Кожна сесія ізольована.

**Концепція: User Storage Layer**

```
┌─────────────────────────────────────────────────────┐
│                USER STORAGE                          │
│  userId: 123456789                                   │
│                                                      │
│  business_process.md      ← бот 1.2 записав         │
│  cashflow_articles.yaml   ← бот 2.1 записав         │
│  pl_articles.yaml         ← бот 2.1 записав         │
│  sheetsUrl                ← бот 2.2 записав         │
│  financial_mechanics.md   ← бот 3.3 записав         │
│  salary_processes.md      ← бот 4.2 записав         │
│  ...                                                 │
└─────────────────────────────────────────────────────┘
       ↑                          ↑
   saveFile нода             loadFile нода
   (будь-який бот)           (будь-який бот)
```

**Що потрібно в API:**

```json
// Записати
{ "type": "saveFile", "data": {
    "fileType": "cashflow_articles",
    "contentVar": "context.result",
    "scope": "user"        // ← прив'язати до userId, не до сесії
}}

// Прочитати
{ "type": "loadFile", "data": {
    "fileType": "cashflow_articles",
    "outputVar": "context.cashflowArticles",
    "scope": "user",
    "onMissing": "block"
}}
```

**Що відображати в UI:**

На сторінці підписника — вкладка "Сховище":
- Список всіх збережених файлів
- Назва, тип, дата запису, який бот записав
- Кнопка "Переглянути вміст" — відкриває файл
- Кнопка "Видалити" — для адміна
- Кнопка "Завантажити" — скачати як .md / .yaml / .json

**Що додати в редактор воронки:**

На канвасі між ботами — візуальний елемент "Сховище" (іконка бази даних) який показує які файли передаються між нодами. Не окрема нода, а overlay/підказка: "Ця нода читає: cashflow_articles" / "Ця нода записує: pl_articles".

## F3. СЛОТИ (Slots) — не питати те що вже відомо

**Проблема:** Якщо студент вже відповів на питання "чим займається компанія" в боті 1.2 — бот 2.1 не повинен питати це знову. Зараз кожен бот починає з нуля.

**Концепція: Named Slots**

Слоти — іменовані поля профілю підписника що заповнюються під час розмови і зберігаються між сесіями.

```
Слоти підписника:
  company_description: "Агентство digital-маркетингу"
  business_type: "послуги"
  client_type: "b2b"
  team_size: "7"
  ...
```

**Як наповнюються:**
1. Claude-нода після відповіді витягує значення і зберігає в слот
2. Або нода "Оновити поле підписника" явно записує

**Як використовуються:**
- При старті наступного бота — Claude отримує заповнені слоти в system prompt автоматично
- Якщо слот заповнений — Claude не питає знову, використовує наявне значення
- Якщо слот порожній — питає

**Що потрібно в API:**

```json
// Нода "Оновити слот"
{ "type": "updateSlot", "data": {
    "slot": "company_description",
    "value": "{{context.extractedDescription}}"
}}

// Передача слотів в Claude-ноду
{ "type": "claude", "data": {
    "injectSlots": ["company_description", "business_type", "team_size"],
    // → автоматично додається в system prompt:
    // "Вже відомо про користувача: company_description=..., ..."
}}
```

**Самоперевірки в критичних місцях:**

Особливо перед побудовою таблиці (боти 2.2, 3.2, 5.2) — Claude перед відправкою до Apps Script виконує self-check:

```
System prompt додаток:
"Перед тим як генерувати OUTPUT_TAG — перевір:
1. Всі статті мають name, responsible, trigger
2. Жодна стаття не дублюється
3. cost_type є у кожної витратної статті і дорівнює cogs/opex/owner/tax
4. Якщо щось відсутнє — запитай перед тим як продовжити, не генеруй неповний OUTPUT"
```

## F8. WHISPER TURBO — self-hosted транскрипція

**Контекст:** Для голосових повідомлень в ботах потрібна транскрипція. Замість платного OpenAI Whisper API — self-hosted рішення.

**Рекомендований варіант: `docker-whisper` (hwdsl2)**

```
GitHub: https://github.com/hwdsl2/docker-whisper
```

Чому саме він:
- OpenAI-сумісний API (`/v1/audio/transcriptions`) → нульові зміни в коді
- Підтримує `large-v3-turbo` — точність large-v3 при половині ресурсів
- Docker — деплоїться на Railway одною командою
- Аудіо не покидає сервер
- Підтримує mp3, m4a, wav, webm, ogg (всі формати Telegram)
- Streaming через SSE

**Деплой на Railway:**
```yaml
image: hwdsl2/whisper
env:
  WHISPER_MODEL: large-v3-turbo
  WHISPER_LANGUAGE: uk      # або auto
  WHISPER_API_KEY: secret
port: 9000
```

**Інтеграція в платформу:**

```json
// В Налаштуваннях
{ "whisperUrl": "https://your-whisper.railway.app",
  "whisperApiKey": "secret" }

// Нова нода: "Транскрибувати аудіо"
{ "type": "transcribe", "data": {
    "inputVar": "context.voiceMessage",  // file_id з Telegram
    "outputVar": "context.transcription",
    "language": "uk"
}}
```

**Альтернатива для CPU без GPU:** `faster-whisper` (CTranslate2) — ~4x швидше ніж оригінальний Whisper на CPU.

## F9. АНАЛІТИКА ПОВЕДІНКИ У ВОРОНКАХ

**Що відстежувати:**

| Метрика | Опис |
|---|---|
| **Conversion rate** | % підписників що дійшли до кожної ноди |
| **Drop-off points** | де найбільше виходять (топ-5 нод відвалу) |
| **Avg completion time** | середній час проходження воронки |
| **Message response time** | скільки чекає між повідомленнями |
| **Re-entry rate** | скільки повертаються після паузи |
| **Slot fill rate** | які слоти заповнюються частіше/рідше |
| **Error rate per node** | % сесій з помилками на кожній ноді |

**Відписки — фіксувати в логах:**

Telegram надсилає webhook `my_chat_member` з `new_chat_member.status = "kicked"` коли користувач блокує бота. Це треба:
1. Записати в лог підписника: `{ event: "unsubscribed", timestamp: ... }`
2. Оновити статус підписника: `active → unsubscribed`
3. Відобразити в аналітиці: графік відписок по часу і по точках воронки

**Воронка поведінки (Funnel visualization):**

```
Старт воронки: 100 підписників
     ↓ 94% (6 відвалилось на Start)
Нода 1 — Intro: 94
     ↓ 87%
Нода 2 — Claude діалог: 82
     ↓ 71%         ← велике падіння, треба подивитись
Нода 3 — Save result: 58
     ↓ 98%
Нода 4 — Завершення: 57
```

Ця візуалізація — прямо на канвасі в режимі "Аналітика" (третій режим поряд з Edit і Live).

| Пріоритет | Фіча | Вплив |
|-----------|------|-------|
| 🔴 Критично | User Storage Layer (`scope: "user"` для saveFile/loadFile) | Без цього файли не передаються між ботами |
| 🔴 Критично | Слоти підписника + `injectSlots` в Claude-ноду | Без цього боти питають одне й те ж двічі |

| 🔴 Критично | Збір профілю підписника (telegramId, username, фото) | Базова інфо яка має бути завжди |
| 🔴 Критично | Фіксація відписок через `my_chat_member` webhook | Втрачені події, некоректна аналітика |
| 🟡 Важливо | Нода "Сповістити адміна" + режим менеджера для Michael Bot | Продажний бот без ручного втручання не закриє угоду |
| 🟡 Важливо | UTM / Deep links — звідки прийшов підписник | Немає атрибуції по джерелах |
| 🟡 Важливо | Тест воронки через API (`test_funnel`) + симулятор в UI | Зараз перевірити бота можна тільки через реальний Telegram |
| 🟡 Важливо | Whisper Turbo self-hosted (docker-whisper) | Голосові повідомлення без платного API |
| 🟡 Важливо | Воронка поведінки (конверсія по нодах) + графік відписок | Немає розуміння де втрачаємо студентів |
