## BUG-001 · `get_connector` не повертає збережені екземпляри

**Статус:** Відкритий  
**Пріоритет:** Середній  
**Виявлено при:** Перебудова Bot 1.1 Onboarding

**Опис:**  
`get_connector` і `list_connectors` повертають тільки *визначення типу* конектора — схему, опис, іконку. Але не повертають збережені екземпляри де вже налаштовані ключі. Через це неможливо через MCP/API вибрати існуючий налаштований конектор і підключити його до ноди.

**Очікувана поведінка:**  
У відповіді `get_connector` додати масив `instances` — збережені екземпляри цього конектора поточного акаунту. Секретні значення не передавати — тільки label і id.

**Пропонована зміна відповіді `get_connector`:**
```json
{
  "id": "ad7582d3-...",
  "name": "Claude Haiku",
  "type": "claude_haiku",
  "schema": { "..." },
  "instances": [
    {
      "id": "inst_abc123",
      "label": "Haiku — Finance Course",
      "has_keys": true,
      "keys_configured": ["api_key"]
    }
  ]
}
```

**Сценарій використання (AI-агент через MCP):**
1. Агент викликає `get_connector(type="claude_haiku")`
2. Бачить `instances` — є вже налаштований екземпляр
3. Запитує користувача: «Використати існуючий чи введеш нові ключі?»
4. Підключає ноду через `instance_id` — секрети не гуляють по API

## BUG-002 · Telegram keys у Bot 1.1 — з'ясовано, не баг

**Статус:** Закрито / пояснено  
**Пріоритет:** —  
**Виявлено при:** Фінальна перевірка воронки Bot 1.1

**Пояснення:**  
`get_funnel` повертає поле `keySource`:
```json
{
  "keySource": {
    "scope": "bot",
    "table": "funnel_keys",
    "inheritedFromProject": false
  }
}
```
Ключі per-bot, не успадковані від проекту. Не баг.

**Рекомендація (не критично):**  
Додати `keySource` у відповідь `list_funnels` (зараз там тільки `keysCount: number`) — щоб одразу було видно scope без окремого `get_funnel`.

## BUG-003 · Тест-сесія ігнорує воронку — запускає вбудований onboarding

**Статус:** Відкритий  
**Пріоритет:** Високий  
**Виявлено при:** Тестування Bot 1.1 Onboarding

**Симптоми:**
- `start_test_session` повертає перше повідомлення яке **не є** жодною нодою з воронки
- `currentState: "interviewing"` — вбудований стан, якого немає в нодах
- `apiCallsCount: 0` після повного діалогу — Claude Haiku жодного разу не викликався
- `nodesVisited: null` — система взагалі не ходила по нодах воронки
- Бот звертається на «вас» хоча в системному промпті прописано «ти»

**Відтворення:**
```
1. Bot 1.1 має кастомну воронку: start → message → claude (Haiku) → saveFile → message
2. start_test_session(botId: "7675fc52-2057-44e2-b0dd-fffa15f99ee9")
3. Відповідь: бот питає «Як до вас звертатись?» — це НЕ нода з воронки
4. Після будь-якої відповіді — apiCallsCount залишається 0
```

**Очікувана поведінка:**  
Тест-сесія має виконувати саме воронку бота — проходити по нодах, викликати Claude-ноди, зберігати файли. Вбудований fallback не повинен перекривати кастомну воронку.

**Гіпотеза:**  
Можливо система розпізнає Bot 1.1 як «onboarding-бот» за slug (`bot-1-1-onboarding`) і підставляє hardcoded flow. Або тригер `/start lesson_1_1` не передається при старті тест-сесії і система падає на fallback.

**Що перевірити розробнику:**
1. Чи є умова: якщо slug містить `onboarding` → використати системний flow?
2. Чи передається trigger `/start lesson_1_1` при `start_test_session`?
3. Чи працює воронка коректно через реальний Telegram (не debug)?
